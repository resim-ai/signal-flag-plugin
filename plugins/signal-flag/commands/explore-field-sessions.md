Load `explore-field-sessions` with `get_skill` from the configured Signal Flag MCP server, using `$ARGUMENTS` or the current request. The served skill owns existing-data discovery and new metric suggestions; `author-metrics-config` owns the existing metric editor, grouped review and configuration publication.

Select the requested environment/account and verify `whoami` before project work. When the request refers to an open page, match its connected browser tab. Preserve existing server/account mappings and reuse identity while context is unchanged. An explicit session or dataset link does not require browser discovery.

Use only data already accessible in the datalake. Do not register sessions, inspect recordings or repositories, install readers, develop emissions, create/register/push metrics builds, configure AWS, or launch evaluations. If required data is unavailable, explain which field or dataset is missing and stop that proposal; do not hand off to another workflow to produce it.

Choose metric names absent from the entire selected base configuration, not just the target set. Recheck after renaming or changing the base. Use self-contained SQL or metrics already in that configuration. Preserve exact historical configuration, batch, job and run pins.

Use real previews when the selected existing instance supports them. If a rendered preview is unavailable, disclose that limitation; never fabricate results or launch a job to unblock it. Saved browser edits and rejection decisions are authoritative. Publishing reusable configuration is distinct from adding a chart to a historical instance. Follow the served review and approval flow, read back the result, and stop after publication.

If the server or skill is unavailable, report the configured environment and connection, authentication or missing-skill problem. Do not invent tools or reconstruct an unavailable workflow.
